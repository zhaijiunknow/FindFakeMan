	一、整体架构策略			
		ManagerA 调用桥接脚本的接口 → 桥接脚本 → 调用 ManagerB 的方法		
				
	GameManager	顶层状态机（启动/标题/探索/检查/暂停/结局），控制全局流程。		
	InteractionManager	管理场景中所有交互点的注册/注销，监听点击事件，协调与 UI 的切换。		
	UIManager	管理所有界面面板，提供显示/隐藏 API，处理屏幕特效。		
	SanityManager	维护 san 值，提供增减接口，san 值归零时触发结局；根据当前 san 值动态调整 UI 效果。		
	InventoryManager	管理收容箱和物品栏；提供物品添加/移除/查询接口。		
	FlagManager	存储剧情标志位，例如“二楼是否解锁”“是否见过某个 CG”；全局唯一真相来源。		
	BranchManager	管理伪人/人类线的随机分支。使用确定性随机种子，保证读档后分支结果一致；每个交互点可单独配置异常概率。		
	EvidenceManager	统计已收集的“基础证据”，达到设定值时触发事件。		
	SaveManager	序列化/反序列化存档，保存 san 值、背包、收容箱、标志位、当前场景、随机种子、已被拾取/破坏的交互点列表。		
	AudioManager	管理 BGM、环境音、UI 音效、角色语音；支持动态参数。		
	SceneManager	封装场景加载，提供加载进度回调，并在场景切换时保持 DontDestroyOnLoad 对象。		
	GameLoopManager	管理关卡内部的核心循环。		
	CGMgr	管理背景图片，播放 CG，支持跳过，播放前后触发事件。		
				
	二、道具系统策略：同一基类 + 两个子类			
				
		2.1 抽象基类 Item		
		仅包含所有道具共有的属性和交互钩子		
				
		标识：itemId、displayName、icon、description		
		交互钩子：OnPickup()、OnDiscard()、OnInspect()、GetAvailableActions()（返回各拖拽方向对应的 ItemAction）		
				
		2.2 子类一：ClueItem（线索道具）		
		职责：证据收集、剧情推进、影响分支走向。		
				
		isAnomaly（是否为伪人线线索）		
		requiresContainment（是否必须进收容箱）		
				
		重写 OnPickup() 时，若为异常线索则强制调用 InventoryManager 放入收容箱而非背包		
		重写 OnDiscard() 时，若为异常线索则强制调用 SanityManager 减 san 值		
		重写 OnInspect() 时根据 isAnomaly 显示不同描述文本		
				
		2.3 子类二：ToolItem（可使用工具）		
		职责：主动调查、解锁交互。		
				
		durability（当前耐久）/ maxDurability		
		toolType（紫外线灯/温度计/探测器等）		
		equippedSlotIndex（占用的物品栏索引）		
				
		OnEquip() / OnUnequip()：更新物品栏 UI，通知 InteractionManager 该工具已装备		
		OnUse()：消耗耐久、执行工具效果（如紫外线灯显示隐藏字迹）		
		重写 GetAvailableActions() 时，确保体感式交互不会产生冲突		
				
	三、动作系统策略：道具基类不直接调用管理器			
				
		3.1 动作的职责		
		每个具体的交互行为（拾取、丢弃、装备、使用、检查）封装为独立的 ItemAction 派生类（如 PickupAction、EquipAction、UseToolAction）。动作负责：		
				
		通过 Services.Get<T>() 调用所需的一个或多个管理器		
		按顺序执行业务逻辑（扣道具、加减 san、设 flag、播 CG）		
		处理动作失败条件（道具满、耐久不足、san 归零）		
				
		3.2 道具基类与动作的协作		
				
		道具基类持有 Dictionary<DragDirection, ItemAction> directionActions，以及 useAction、discardAction 等快捷动作引用。		
		提供 ExecuteAction(DragDirection dir) 方法，内部查找对应动作并调用 Execute()。		
		道具基类完全不感知管理器的存在——它只依赖 ItemAction 抽象。		
				
		3.3 动作调用不同管理器的典型映射		
				
		动作类型	调用的管理器	说明
		PickupAction	InventoryManager、SanityManager	检查容量 → 添加到收容箱 → 设标志位
		DiscardAction	InventoryManager、InteractionManager	移除道具 → 异常物品扣 san → 设标志位
		EquipAction	InventoryManager、UIManager	检查容量 → 装备到装备栏 → 更新 UI → 设标志位
		UseToolAction	InventoryManager、SanityManager	减耐久 → 耐久归零则卸下 → 设标志位
		UseConsumableAction	SanityManager、InventoryManager	恢复 san → 移除道具 → 设标志位
		InspectAction	UIManager、FlagManager	显示描述 → 首次检查则设标志 → 设标志位
				
	四、交互与拖拽系统策略			
				
		4.1 交互点配置		
		场景中每个可交互对象挂载 SimpleInteractable 组件，配置：		
				
		关联的 Item 实例（从 ItemData ScriptableObject 运行时创建）		
		每个拖拽方向（上/下/左/右）对应的 ItemAction（可直接引用动作资源）		
		伪人线概率 anomalyChance 及伪人线时是否替换动作/描述		
				
		4.2 精查界面流程		
				
		玩家点击交互点 → InteractionManager 通知 UIManager 打开 InspectorUI，并传入当前道具实例。		
		UI 面板显示道具图标、名称、描述，并根据 item.GetAvailableActions() 动态显示四个方向的提示图标（如“装备”“拾取”“丢弃”“检查”）。		
		玩家拖拽（距离超过阈值）→ UI 检测方向 → 调用 item.ExecuteAction(direction) → 动作执行 → 关闭面板。		
		若拖拽距离小于阈值（轻点）→ 仅显示详细描述（调用 InspectAction 或内联显示），不关闭面板。		
				
		4.3 使用道具流程		
				
		拖拽工具到交互点 → 直接执行工具交互		
		如果玩家在拖工具 → 不触发点击精查		
				
		4.4 状态机切换		
		点击交互点时，GameManager 状态从 Exploration 切换到 Inspection，暂停其他交互。动作执行完毕后切回 Exploration。		
				
	五、数据持久化策略			
				
		5.1 存档内容		
				
		全局数据：san 值、随机分支种子、当前场景、已解锁区域		
		背包/收容箱/装备栏：每个道具的 itemId 及运行时状态（耐久、异常标记）		
		标志位字典（FlagManager）		
		已被拾取/销毁的交互点 ID 列表		
				
		5.2 读档流程		
				
		加载目标场景。		
		反序列化 JSON。		
		恢复各管理器状态（通过 Services.Get<T>().LoadState(data) 接口）。		
		遍历场景中的 SimpleInteractable，若其 itemId 在销毁列表中则禁用。

	八、可复用视觉小说系统						
	能跑序章现在的所有内容——新闻播报、花屏、内心独白、联络员通讯、档案展示、装备检查						
	能跑后续所有章节——因为后续会有大量类似的叙事段落						
	能方便地扩展新功能——比如条件分支、选项肢、多结局统计、QTE						
							
		剧本数据层（纯数据）					
		ChapterConfig.json / .asset / Excel导出					
		包含：所有章节、序列、节点、角色、立绘、CG、音频					
		↓					
		剧本引擎层（可复用核心）					
		VNDirector / VNSequence / VNNode / VNBranch					
		职责：解析数据、控制播放、管理跳转、执行特效					
		↓					
		桥接适配层（对接MOM）					
		VNBridge / VNChoiceBridge / VNEventBridge					
		职责：将引擎指令翻译为Manager操作					
		↓					
		表现层（Managers + UI）					
		UIManager / CGMgr / AudioManager / FlagManager					
		职责：响应指令，执行具体表现，不做逻辑判断					
							
	核心原则：引擎层和表现层完全解耦。引擎只管「播到哪了」「下一步是什么」「要不要等玩家输入」「满足什么条件才能跳转」——它不知道也不关心背景图怎么切、音乐怎么渐变。桥接层负责翻译。						
							
	剧本数据层设计						
							
	Chapter（章节）						
	└─ Sequence（段落）						
		└─ Node（节点）					
			└─ Block（块，可选，用于嵌套）				
							
	节点代表一次完整的画面呈现。一个节点包含：						
							
	文字内容						
		说话人是谁（可以为空，表示旁白或叙述者）					
		正文内容是什么					
		内容是否需要打字机效果（逐字显示）					
		打字速度（每字符多少秒）					
							
	视觉呈现						
		使用哪张背景图					
		是否播放CG（CG优先级高于背景图）					
		是否叠加屏幕特效（花屏、闪烁、抖动、淡入、淡出）					
		是否显示立绘（哪个角色、第几个表情、从哪边进来）					
		立绘位置（左、中、右）					
							
	声音						
		是否播放语音（哪个音频文件）					
		语音结束后是否自动进入下一节点					
		是否播放音效（比如花屏杂讯）					
		是否切换BGM（切到哪首、如何过渡）					
							
	逻辑控制						
		这个节点播放完后要设置哪些flag					
		是否需要等待玩家点击才能继续					
		是否有条件判断（满足什么条件才播这个节点）					
		下一节点是谁（默认按顺序，也可以显式指定）					
							
	序列是一组节点的集合，代表一个完整的叙事段落。						
							
	一个序列需要定义：						
		这个序列叫什么（ID）					
		序列播放前做什么（进入条件）					
		包含哪些节点（按顺序）					
		序列播放完后自动跳转到哪个序列（可以为空，表示序列结束交给外部处理）					
		是否有结束条件（比如flag判断）					
							
	章节是顶层容器						
							
	一个章节需要定义：						
		章节ID（用于存档和跳转）					
		章节标题（显示用）					
		入口序列（从哪个序列开始播放）					
		章节内所有序列的列表					
		章节开始前需要满足的条件					
		章节结束后自动进入什么（下一个章节Scene？还是自由探索模式？）					
							
	剧本引擎层设计						
							
	核心职责						
							
	维护当前播放状态						
		当前在哪个章节					
		当前在哪个序列					
		当前在哪个节点					
		当前是否在等待玩家输入					
		当前是否正在播放自动序列（比如连续自动推进的花屏）					
		当前有哪些flag可以查询					
							
	解析节点，执行指令序列						
		一个节点可能同时要求：切换背景 + 显示文字 + 播放语音 + 播放特效 + 设置flag + 切换音乐。					
		这些操作需要按正确的顺序执行，有些可以并行（比如文字显示和BGM播放），有些必须等前一个完成（比如花屏必须等特效播完才能切到下一节点）。					
							
	处理跳转逻辑						
		按顺序播放下一个节点					
		跳转到指定节点					
		跳转到另一个序列					
		跳转到另一个章节					
		等待玩家选择（选项节点）					
		等待外部信号（比如CG播放完毕）					
		结束					
							
	条件判断						
		某个角色的隐藏对话只有在特定flag为true时才播放					
		二周目时跳过序章直接进入					
		某个选项选了A之后，后续序列走向不同					
							
	节点执行流程						
							
	第一步：条件检查						
		检查这个节点是否有 条件 字段					
		如果有，查询 FlagManager 判断是否满足					
		满足 → 继续					
		不满足 → 查找备选节点（elseNode 字段）或者跳过这个节点播下一个					
							
	第二步：设置Flag（立即执行）						
		把 设置Flag 列表里的所有flag写入FlagManager					
		这步在视觉呈现之前就执行，确保后续逻辑能立即感知到变化					
							
	第三步：背景与CG处理						
		调用桥接脚本，切换背景图或播放CG					
		如果有淡入淡出特效，等待过渡完成					
		这里允许背景和CG同时存在——比如背景是新闻演播室，CG叠加一个花屏帧					
							
	第四步：立绘处理						
		根据节点里定义的立绘信息，调用桥接脚本显示/隐藏/切换立绘					
		支持淡入淡出和滑入滑出动画					
							
	第五步：声音处理						
		播放语音（异步，不阻塞）					
		播放音效					
		切换BGM（异步，带crossfade）					
							
	第六步：文字显示						
		调用桥接脚本，把说话人和正文内容传给UIManager					
		启动打字机效果（如果配置了）					
		如果 自动继续: true，则在打字完成后自动进入下一节点					
		如果 等待点击: true，则等待玩家点击才继续					
							
	第七步：特效处理						
		调用桥接脚本，播放节点里配置的所有特效					
		某些特效需要阻塞（比如花屏0.3秒内禁止玩家点击）					
		某些特效不阻塞（比如淡入淡出可以和其他内容并行）					
							
	第八步：播放完毕，准备下一步						
		如果是 等待点击 → 引擎进入「暂停」状态，等玩家输入					
		如果是 自动继续 → 引擎自动计算下一节点并继续播放					
		如果有 下一节点 显式指定 → 跳转到指定节点					
		如果有 自动跳转序列 → 跳转到另一个序列的开头					
							
	序列执行流程						
							
	第一步：检查进入条件						
		查询FlagManager					
		不满足 → 跳过这个序列，播放下一个（或者报错，取决于配置）					
							
	第二步：按顺序播放所有节点						
		对每个节点执行「节点执行流程」					
							
	第三步：处理序列结束						
		如果有 自动跳转 → 播放下一个序列					
		如果有 结束条件 → 判断是否满足，满足则结束章节					
		如果都没有 → 向外部发送「序列播放完毕」信号，交给上层处理					
							
	章节执行流程						
							
	第一步：检查章节开始条件						
		满足 → 加载章节数据，切换到对应Scene					
		不满足 → 跳转到备选章节或显示提示					
							
	第二步：执行入口序列						
							
	第三步：序列完成后，处理章节结束行为						
		可以跳转到下一个章节					
		可以切换到自由探索模式					
		可以显示结局画面					
		可以自动存档
